## 🔄 Migration History

### Version 1 → 2: Transaction Type Support
**Added:** `transaction_type` column to `bank_notifications`
- Enables tracking of EXPENSE vs INCOME transactions
- Nullable field for backward compatibility

### Version 2 → 3: Account Number Matching
**Added:** `accountNumberLast4` column to `bank_accounts`
- Stores last 4 digits for SMS transaction matching
- Nullable field

### Version 3 → 4: Payment Method Tracking
**Added:** Payment method fields to `expenses`
- `paymentMethod` (TEXT) - e.g., "UPI", "Cash", "Card"
- `paymentIcon` (TEXT) - Icon identifier
- Both nullable for backward compatibility

### Version 4 → 5: Bank Account Linking
**Added:** `bankAccountId` foreign key to `expenses`
- Links expenses to specific bank accounts
- Nullable - expenses can exist without account assignment
- Index created for query performance

### Version 5 → 6: Salary Calculation Control
**Added:** `includeInSalary` column to `projects`
- Boolean flag (default: true)
- Controls whether project expenses count toward salary calculations

### Version 6 → 7: Category Icons
**Added:** `emoji` column to `categories`
- Default value: "▶️"
- Enables visual category identification

### Version 7 → 8: Expense-Asset Linking
**Added:** `expenseId` column to `assets`
- Nullable foreign key to expenses
- Enables direct expense-to-image association

### Version 8 → 9: Enhanced Salary Tracking
**Added:** Multiple fields to `salary_records`
- `linkedAccountId` (INTEGER, default: 0) - Required bank account link
- `sourceType` (TEXT, default: "PRIMARY") - Income source type
- `sourceName` (TEXT, default: "") - Display name for income source
- `autoGenerated` (BOOLEAN, default: false) - Auto-generated flag
- `isActive` (BOOLEAN, default: true) - Active status
- `recurringAccountId` (INTEGER, nullable) - Legacy field for compatibility

### Version 9 → 10: Trash Management
**Added:** Trash-related fields to `bank_notifications`
- `rejectedAt` (TEXT/LocalDateTime) - When transaction was rejected
- `deletion_scheduled_at` (TEXT/LocalDateTime) - Scheduled deletion time
- `trash_retention_days` (INTEGER) - Days to keep in trash
- Index created on `deletion_scheduled_at` for cleanup queries

### Version 10 → 11: Unrecognized SMS Tracking
**Created:** `unrecognized_sms` table
- Stores SMS from financial providers that couldn't be parsed
- Unique constraint on (sender, sms_body) to prevent duplicates
- Supports user reporting for parser improvements

### Version 11 → 12: Merchant Auto-Categorization
**Created:** `merchant_rules` table
- Pattern-based auto-categorization for SMS transactions
- Priority-based rule matching
- Usage tracking (match_count, last_matched_at)
- Indices on merchant_pattern, priority, and is_active

### Version 12 → 13: Schema Validation
**Purpose:** Ensure all bank_accounts fields exist
- Handles cases where table was created in older versions
- Adds missing `accountNumberLast4` if needed
- Uses try-catch for idempotent migration

### Version 13 → 14: Index Optimization
**Purpose:** Performance optimization and data integrity
- Created indices on frequently queried columns
- Ensured foreign key indices exist
- Added unique constraints for data integrity
- Optimized query performance for:
  - Expense lookups by category, bank account, and date
  - Category lookups by project
  - Bank notification status and deletion queries

## 🛠️ Migration Best Practices

### 1. **Always Preserve User Data**
```kotlin
// ❌ NEVER DO THIS in production
.fallbackToDestructiveMigration()

// ✅ ALWAYS provide explicit migrations
.addMigrations(MIGRATION_X_Y, MIGRATION_Y_Z)
```

### 2. **Use Default Values for NOT NULL Columns**
```kotlin
database.execSQL(
    "ALTER TABLE table_name ADD COLUMN new_column TEXT NOT NULL DEFAULT 'default_value'"
)
```

### 3. **Create Indices for Foreign Keys**
```kotlin
database.execSQL(
    "CREATE INDEX IF NOT EXISTS index_table_column ON table(column)"
)
```

### 4. **Test Migration Paths**
- Test upgrade from each version to the next
- Verify data integrity after migration
- Check foreign key constraints
- Validate query performance

### 5. **Handle Nullable vs NOT NULL Carefully**
- New columns should be nullable OR have default values
- Existing data must remain valid after migration

## 🚨 Common Migration Issues

### Issue 1: Column Already Exists
**Symptom:** `duplicate column name` error
**Solution:** Use try-catch or check schema version
```kotlin
try {
    database.execSQL("ALTER TABLE...")
} catch (e: Exception) {
    // Column already exists
}
```

### Issue 2: Foreign Key Constraint Violation
**Symptom:** Migration fails with constraint error
**Solution:** 
- Ensure parent table exists first
- Use `SET NULL` or `CASCADE` appropriately
- Create indices for foreign keys

### Issue 3: Data Loss on Update
**Symptom:** User data disappears after update
**Solution:**
- Remove `fallbackToDestructiveMigration()`
- Provide explicit migration for every version change
- Test migration path thoroughly

## 📝 Adding New Migrations

### Step-by-Step Process

1. **Modify Entity Class**
   ```kotlin
   @Entity(tableName = "expenses")
   data class Expense(
       // ... existing fields
       val newField: String? = null  // Add new field
   )
   ```

2. **Increment Database Version**
   ```kotlin
   @Database(
       entities = [...],
       version = 15,  // Increment version
       exportSchema = true
   )
   ```

3. **Create Migration**
   ```kotlin
   private val MIGRATION_14_15 = object : Migration(14, 15) {
       override fun migrate(database: SupportSQLiteDatabase) {
           database.execSQL(
               "ALTER TABLE expenses ADD COLUMN newField TEXT"
           )
       }
   }
   ```

4. **Add to Migration List**
   ```kotlin
   .addMigrations(
       // ... existing migrations
       MIGRATION_14_15
   )
   ```

5. **Test Migration**
   - Install v14, add data
   - Install v15, verify data preserved
   - Check new field works correctly

6. **Document Migration**
   - Update this guide
   - Add comments in code
   - Update schema export
